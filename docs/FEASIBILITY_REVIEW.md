# FinSight AI 方案可行性与优化评审

评审日期：2026-10-28（Asia/Shanghai）  
依据：`FinSight_AI_Codex_Implementation_Brief.md` 原始说明书。  
范围：响应用户“首先检查文档方案是否可行、是否有优化空间”。本轮完成评审和开发任务拆解，尚未进入应用编码或运行验收。文档末尾的“立即开始阶段 1”作为后续开发要求，不改变本轮先评审的顺序。

## 1. 结论

**方案可行，建议保留产品边界和技术栈，在编码前补齐财务口径、证据验证、异步任务及部署边界。**

Vue 3 + FastAPI + PostgreSQL + Redis 能承载要求的业务。优先无 AI 数据闭环、后端确定性计算、SEC 作为来源、模型适配器和可追溯引用的方向正确。四家模型服务可以逐一接入；它们的账号、网络和实际模型调用能力需要分别验证，不能由接口文档推导为“已经可用”。

项目主要难点是数据是否可比、研究结论是否受到证据支持，以及失败后能否恢复。建议按原五个 P0 阶段推进，P1/P2 保持延后。第一阶段应交付一个较小但真实的纵向闭环，不能以全部页面的静态演示代替。

SEC 官方确认 submissions/companyfacts 为无需 API Key 的公开接口，事实聚合范围限于标准 taxonomy、申报主体整体数据；因此它适合本项目的基础指标，但不保证完整覆盖所有财务披露。部署还需遵守访问政策。[SEC API 文档](https://www.sec.gov/search-filings/edgar-application-programming-interfaces)

## 2. 编码前必须补齐的规则

### 2.1 将可加指标与不可加指标分开

文档的 YTD 差分和 FY−9M 规则应只用于同口径的可加期间金额，例如收入、净利润、经营现金流。**稀释 EPS、利润率和加权平均股数不可直接差分。** EPS 涉及各期间不同的加权股数和稀释计算；仅凭全年和九个月 EPS 不能可靠推出第四季度 EPS。

实现约束：每个指标定义 `period_kind`、`aggregation_rule`、允许单位和候选 concept。EPS 优先使用明确披露的单季度值；没有足够依据时返回 `null` 和 `NON_ADDITIVE_METRIC`。同比遇到零或负基期，默认返回 N/A 并显示绝对变化和说明。

Apple FY2023 官方年报的 EPS 计算使用加权平均股数，并披露当年为 53 周财年；因此这两项边界都直接涉及目标演示公司。[Apple FY2023 10-K](https://www.sec.gov/Archives/edgar/data/320193/000032019323000106/aapl-20230930.htm)

差分必须验证 concept、单位、财年起点、期间嵌套关系和重述口径。两个值都被映射成 `revenue` 不足以证明可以相减。出现冲突时返回不可比状态，不按候选标签排序强行取值。

### 2.2 分离“最新重述口径”和“指定财报口径”

文档提出“最新有效申报”，但研究指定旧财报时若自动替换成后续重述值，会造成时间穿越。

建议公司概览默认 `latest_restated`，显示截止披露日期；指定财报研究使用该 accession 的可用事实并冻结快照。需要历史时点比较时，显式设置 `as_of` 截止时间。不得无提示地回退到后来的事实。

对同一期间保留多版本原始事实、选取理由和规则版本。修订表单不一定重述每个财务指标，不能仅因 `10-K/A` 披露更晚就覆盖整份财报。财年由实际 `start/end` 与财年边界判定；`fy/fp/frame` 作为辅助证据，不能直接作为事实期间的唯一标签。52/53 周财年须有测试，不能只按固定 365/90 天分类。

### 2.3 来源存储从第一阶段开始

建议在建议表之外增加少量基础实体或等价字段：

| 对象 | 最少信息 | 目的 |
|---|---|---|
| `source_snapshots` | 官方 URL、获取时间、内容哈希、原始响应引用、`source_kind` | 可重放解析，区分真实快照和合成夹具 |
| `sync_jobs` | CIK、状态、重试次数、错误码、开始/结束时间 | 支持同步进度、恢复和幂等 |
| 财务期间 | 实际起止、FY/FQ、时点/期间、判定依据 | 统一财年与季度规则 |
| 规范化结果 | 原始 fact ID、计算输入、规则版本、缺失原因 | 可解释每个展示值 |

离线数据区分 `sec_live`、`sec_snapshot`、`synthetic_fixture`。真实历史快照显示采集时间；合成数据不能仅贴 SEC 标识。fixture 与真实数据使用独立数据库或命名空间，不能依赖前端一个横幅隔离。在线失败保留旧缓存并标注陈旧，不能静默切换成演示数据。

`financial_facts.raw_context_json` 应明确保存的是 companyfacts API 原始行，不等于完整 XBRL 实例的 contextRef、维度和精度信息；缺少自定义 taxonomy 或分部事实时给出缺失原因。

数据库采用 `NUMERIC`，Python 采用 `Decimal`；API 精确值建议编码为十进制字符串或 `null`。前端图表可转换显示数值，但不参与业务计算，表格保留精确原值。仅后端使用 Decimal、随后序列化成浮点数仍可能损失精度。

### 2.4 异步基础提前到第一阶段

第一阶段已有 SEC 同步任务和 202 响应，不能等到阶段四才引入真正队列。推荐 **Redis + RQ**，后台使用 Linux 容器；阶段四在同一机制上增加研究任务。

补齐 `GET /api/v1/sync/jobs/{id}`。任务先持久化后入队，处理入队失败和进程崩溃后的恢复。相同公司重复同步应合并或复用在途任务；数据库约束保证重复执行不产生重复事实。不能声称任务系统天然提供 exactly-once。

SEC 限速必须覆盖 API 与所有 worker。建议共享 3 QPS 的平滑限速、缓存与在途请求合并；429 尊重 `Retry-After`，403 记录诊断并冷却，不能持续重试。SEC 当前公布上限为每秒 10 次，项目使用更低限制是合理的。[SEC 访问政策](https://www.sec.gov/search-filings/edgar-search-assistance/accessing-edgar-data)

标准 worker 在 Linux 容器中统一运行，避免将 Windows 特定的 worker 差异带入正式验收。具体 worker 的平台和心跳限制应按锁定版本验证。[RQ worker 文档](https://python-rq.org/docs/workers/)

队列与 worker 显式采用一致的 JSON serializer，任务参数仅传 job/config ID，不把 Key、完整原文或解密后的配置写进 Redis。Compose 配置 PostgreSQL/Redis 健康检查和一次性迁移服务，API/worker 等待迁移成功；容器已创建不代表依赖就绪。[Docker 启动顺序](https://docs.docker.com/compose/how-tos/startup-order/)

### 2.5 引用有效不等于结论正确

现有示例 schema 的 `summary` 是无引用字符串；仅检查 `citation_id` 存在，无法满足“每个实质事实可回溯”的验收要求。

建议把摘要和分析拆成带证据的 claims；区分披露事实、计算结果、模型推论和未知项。每项包含引用或 metric ID。后端从已保存片段填充出处和摘录，不能采用模型自行提供的 URL、摘录或数值。

验证分层：schema 合法性；引用属于本次上下文；摘录与来源一致；指标、单位和期间一致；结论是否被证据支持。前四层适合确定性检查；最后一层不能仅靠 Pydantic 保证，需要固定样本评测和人工抽检。界面不能把“引用通过校验”写成“结论已证实”。结构化输出仍可能包含错误，官方文档亦明确指出这一限制。[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

模型自由文本中的数字也可能错误。建议财务数值由后端模板注入，模型只引用 `metric_key/period`；检测到无法验证的数值或无证据断言时，有限重试后标记证据不足。任务、报告和缓存记录模型 ID、配置版本、prompt/schema 版本、检索方式、文档哈希、指标快照与规则版本。

### 2.6 处理中文问题与英文材料的检索落差

PostgreSQL 英文 FTS 能处理英文词项与词典，但不应假设它会把中文问题自动转换成英文证据查询。该缺口来自“中文优先问答 + 英文 SEC + 无 embedding 降级”的组合，是对方案的工程判断。[PostgreSQL FTS 配置](https://www.postgresql.org/docs/current/textsearch-configuration.html)

P0 采用章节定位、英文 FTS 和小型中英金融术语表；可用模型时允许受限的查询改写。未知词和低召回明确提示，不能把无命中描述成“财报不存在该风险”。pgvector 与本地 embedding 保留后续启用，不作为第一阶段启动前提。

至少以中文问题测试收入变化、毛利、现金流、风险和两期比较；不能只测试英文问题。

### 2.7 明确本地单用户与公网服务的边界

建议首版选择私有单用户部署，保留后端固定 owner 和权限依赖。设置、Key 测试、同步及付费研究调用均需要可信会话；不要将“单用户”实现成任何访客都能写配置或触发计费。数据库、Redis 和 Ollama 不对公网开放。

环境变量配置与 UI 加密保存共享适配器；加密主密钥缺失时禁用保存操作并解释原因，不能生成临时密钥导致重启后凭据失效。浏览器仅短暂持有用户正在输入的 Key；日志和错误体不记录请求密钥。HTTPS 适用于远程部署，本机回环开发需要单独写清边界。

Ollama 目标由部署者预设，普通用户只能选择地址标识。只检查初始域名不足以阻止恶意重定向，HTTP 客户端也需要约束重定向与最终目的地。公网多用户版再启用独立用户、RBAC 和逐用户数据隔离；不得以当前本地模式宣称已完成多租户安全。

### 2.8 8-K 正文和附件的证据范围

事件列表可以先展示元数据。事件研究则需识别主文与附件的差别：主文不一定包含业绩发布的完整信息。对已选 accession，只从官方目录内按类型与大小限制获取必要附件，例如 EX-99.1；附件也保存独立来源。

若 P0 暂不支持某类附件，应返回“主文证据不足/附件尚未解析”，不能把短主文当作完整业绩公告。数据源可能出现附件、表格和 Inline XBRL，解析需保留章节、表格标题和上下文，不能简单拼接所有文本。

## 3. 模型适配方案核查

| 服务商 | 核查结论 | 实现要求 |
|---|---|---|
| OpenAI | 模型枚举接口存在；返回基本信息不等于完整能力声明 | 官方 SDK；以实际小调用验证指定 ID，不猜测上下文和参数能力 |
| DeepSeek | `/models` 可枚举；当前文档还提供部分能力元数据 | 使用真实返回字段，兼容缺字段；能力以协议与调用结果为准 |
| Gemini | 支持模型列表、分页与生成方法元数据 | Google GenAI SDK，处理分页并筛选 `generateContent` |
| Ollama | `/api/tags` 提供模型列表；兼容 API 只覆盖部分能力 | 本地模式用明确本地模型及受控地址，不能将所有兼容能力视为一致 |

来源：[OpenAI models](https://developers.openai.com/api/reference/resources/models/methods/list)、[DeepSeek models](https://api-docs.deepseek.com/api/list-models/)、[Gemini models](https://ai.google.dev/api/models)、[Ollama tags](https://docs.ollama.com/api/tags)、[Ollama compatibility](https://docs.ollama.com/api/openai-compatibility)。

保留四个 provider 的 P0 目标，逐个实现并通过契约测试。连接验证绑定 provider、model ID 和配置版本；更换模型或 Key 后作废旧验证。最多有限重试，取消需区分本地停止等待与上游请求确已取消。拒答、输出截断、错误 JSON 都应有明确失败状态。

## 4. 推荐架构与推进顺序

采用模块化单体：Vue → FastAPI → PostgreSQL；FastAPI → Redis/RQ → worker → SEC/LLM。前后端共享 OpenAPI 契约，worker 与 API 共享业务服务与模型。无须增加微服务、独立向量数据库或自建通用 Agent 平台。

| 阶段 | 交付与验收重点 | 本次建议 |
|---|---|---|
| 1 无 AI 闭环 | 搜索 → 公司 → 同步状态 → 年度指标 → 申报/事件列表 | 先做收入、净利润、资产、负债、经营现金流；同时打好来源、队列、错误格式基础 |
| 2 财务口径 | 补齐十项指标、季度/YTD/Q4、同比/比率、来源详情 | 先通过纯函数测试，再接入 API；冻结真实快照与专用边界夹具 |
| 3 模型配置 | 四 provider、手动模型、连接测试、加密配置 | 最简 AI 概览引用阶段二的结构化事实，不依赖尚未实现的 HTML RAG |
| 4 研究报告 | HTML/受控附件解析、检索、引用、事件解读、历史下载 | 复用阶段一队列，加入证据不足与模型失败状态 |
| 5 可展示交付 | 集成与浏览器测试、部署说明、CI、运行截图 | 截图必须来自成功启动；公网资源未提供时不宣称已上线 |

CI 分两层：无需外网和 Key 的单元/契约测试；真实 PostgreSQL + Redis 服务的迁移和集成测试。浏览器端到端覆盖搜索、图表、模型配置、Fake Provider 研究、引用和下载。Fake 只用于测试/显式演示模式，不能成为生产环境静默替代。

“离线可验收”应定义为依赖和容器镜像准备好后，测试过程无需访问 SEC/LLM；全新机器在没有依赖缓存且完全断网时不能凭空完成安装。

## 6. 第一阶段的验收门槛

1. 从空数据库执行 Alembic 迁移，启动 API、worker 和前端。
2. 无 Key、无 Ollama 时，三个目标公司的搜索、年度指标、10-K/10-Q/8-K 列表可用；真实数据/历史快照/合成夹具标记准确。
3. 每个展示值能展开期间、单位、accession、披露日期和选取依据；缺失值及原因可以区分。
4. 同步返回任务 ID，重复点击不产生重复工作；SEC 限流、失败和旧缓存场景能解释并恢复。
5. 实际执行后端测试、ruff、前端类型检查/lint/build；使用 PostgreSQL/Redis 的集成结果单独报告。

后续从 `docs/TASKS.md` 的阶段一开始。上述修订细化原需求，不扩大 P0 市场覆盖，也不移除原文要求的四家模型支持。
